# 第二轮图像工程验证与性能记录

2026-10-17，审阅基线 Suite v1.4.19 / Studio 0.1.19。用户已确认当前素材尚未人工标注，先完成工程验证。本记录严格区分公开真实来源变换回归、私有原图本地操作验证与尚未进行的独立人工盲测。

## 已完成与证据边界

当前引擎筛查不同图片之间的像素相同、变换同源和局部重叠；不支持单张压平图片内部的复制粘贴区域检查。局部定位要求共同来源与严格双向几何证据，拒绝定位会保留原因，不猜框。没有检出不能说明没有重复。

| 层级 | 素材和标签来源 | 已测范围 | 可以支持的结论 |
| --- | --- | --- | --- |
| 公开工程回归 | 6 个公开源文件、7 张分析图；变换参数和不相交裁剪由脚本构造 | 70 对，H&E、IHC、荧光、SEM、TEM、Western blot；每个案例完整记录 | 固定这些真实来源、固定变换下的可复现行为和已知难例 |
| 私有本地工程回归 | 用户许可本机验收，3 个指定目录；选取 9 张源图构造标签，其中 TEM 明确只用指定原生 ROI | 82 对，切片/荧光外观、用户声明的 Western blot 与原生 uint16 TEM 局部 | 私有素材在已写明文件/视野范围内的检测及定位行为；不代表全幅大 TIFF 可用 |
| 独立真实案例盲测 | 用户尚未提供独立人工标签 | **未测** | 不能声称代表性真实科研图片的灵敏度、特异度或临床可靠性 |

变换复制不等于真实不当使用，也不代表学术不端。相同样本不同视野、不同通道、共享对照、真实采集倍率变化等，需要采集记录和人工判断；当前工程集合不能替代此类盲测。为性能生成的 60 张合成图也不进入准确率分母。

6 个查重漏检：TEM 重裁剪；blot C 的复合裁剪与重裁剪；blot D 的亮度/对比度/JPEG、一般裁剪、重裁剪。Western blot 低细节、极狭长和小范围截取是明确难例，不据此放宽阈值制造似是而非的匹配。

## 私有素材验收和完整性

私有清单、路径映射、原始字节副本、联系表和截图只留在 `.cache/round2-private/`，不进入公开提交或安装包。图像只获得本机使用许可，不能因为匿名命名就视为可分发。公开说明不包含原文件名、绝对源路径、实验组或实验记录。

首批 5 张真实来源构造 50 对：精确身份 5/5 PASS；TP 44、FN 1、FP 0、TN 5。漏检为一张切片外观图的约 4% 面积裁剪。定位阳性 14/15 正确返回，5 个阴性不返回坐标。它们属于本地适配工程验证，模态按外观暂记，不能当作研究诊断或独立标签。

随后根据用户新增目录分别审计 54 张 WB 单页 8 位灰度 TIFF、19 张 TEM 原生 uint16 TIFF，仍无独立人工标签。新增小样本结果见 [脱敏分层汇总](qa/round2/private-image-engineering-summary.json)：

| 本地集合 | 构造对数 | TP / FP / FN / TN | 原生/精确身份 | 正确定位 / 阳性 | 阴性错误定位 |
| --- | ---: | --- | --- | --- | --- |
| 首批切片/荧光外观 | 50 | 44 / 0 / 1 / 5 | 5/5 | 14/15 | 0/5 |
| WB，2 张源图 | 20 | 16 / 0 / 2 / 2 | 2/2 | 0/6 | 0/2 |
| TEM，2 张原生 uint16 **指定局部** | 12 | 10 / 0 / 0 / 2 | 2/2，PNG↔无损 TIFF | 4/4 | 0/2 |

WB 两个重裁剪漏检。6 个 WB 定位阳性全部因空间支持不足而拒绝，没有为了成功率调松门槛。TEM 指定局部的返回候选 IoU 中位数 0.9992，角点最大误差 P95 为 1.01 个局部原图像素；它们是已知构造 ROI 的结果，仍不代表真实不同倍率采集的自动对应能力。

**真实 TEM 全幅限制：**19 张原生 TIFF 均超过当前每图 12,000,000 字节的检查边界；按实际宽高核查，它们均未超过 20 百万像素，文件大小超限与像素数边界是两件不同的事。选中两张全幅 TIFF 约 16.9 MB，无损封装为原生 uint16 PNG 后仍约 14.3 MB，均不能直接全图检查。没有静默转 8 位、压缩成有损 JPEG 或缩图来伪装通过。额外工程分析明确取原图中央 80% 宽、高的指定 ROI，保留原生 uint16，每个像素与原图该区域完全一致；该局部 PNG 约 9.5/9.6 MB，处于已支持范围。全幅封装、指定 ROI、位深/形状/逐像素一致性证明和原始路径均留在私有记录。

[真实 HTTP 接口的 6 个匿名案例](qa/round2/private-raster-api-summary.json)实际使用带授权的 127.0.0.1 端点：WB 原始 8 位 TIFF 与 PNG 精确一致；WB 定位拒绝且说明空间不足；TEM 指定原生 uint16 ROI 的 PNG/无损 TIFF 精确一致、定位返回正确区域；原始超限 TEM TIFF 和全幅原生 PNG 均明确返回 12 MB 限制。所有预期 PASS；超限案例的 PASS 指**正确拒绝**，不表示查重成功。未授权 HTTP 请求另验证为 403。

上述 6 个案例还在实际安装的 **Studio 0.1.20 / Suite 1.4.20 Windows x86_64** 服务中重跑，[安装版记录](qa/round2/windows-private-raster-api-summary.json)全部 PASS。客户端仅发送原始编码字节至该已安装程序，没有启动源码分析服务，实际解码、原生哈希、SIFT 和边界判断由冻结的 Pillow/OpenCV 执行。首次尝试恰逢另一个 UI 查重任务，3 次响应为“已有任务运行”；该轮记录为并发干扰、不能用于位深或容量结论。确认服务空闲后再执行；容量测试要求错误文字具体包含 `12 MB`，不能用任意报错充当通过。

另外在一个**派生副本**中仅改变一个像素的 uint16 最低有效单位，安装版返回不同原生哈希且没有报告 exact（仍有正常同源候选），验证没有因 8 位截断把不同原生像素当成完全相同。该项是位深工程回归，不加入真实案例准确率统计，原始文件不变。

最终重新只读核对三个授权目录共 **240 张原始图像的文件 SHA-256，240/240 不变**。公开报告只含匿名工程统计，不包含私有素材、原文件名、源绝对路径或实验测量记录。

`scripts/audit_private_image_corpus.py --source <用户指定目录> --out <私有本地目录>` 只读清单，匿名原图副本保持原始字节。添加 `--verify` 会重新核对该授权目录内的源文件与先前散列，拒绝访问目录外的映射。未经过独立人工标注的原图对保持 unknown，不能自动计为阴性。

普通用户的当前边界：单张最多 12 MB、20 百万像素，每批 2–60 张、编码后合计 40 MB；格式接受 PNG/JPEG/WebP/GIF/TIFF/BMP 的单页栅格。多页/动画需明确逐帧处理，不能把压平组图内部区域当作多张图。超过边界时保留原始文件，先按明确范围导出符合限制的**无损、保留位深**副本或局部再检查；该结果只覆盖导出的范围。Gallery 常规图片导入与查重对话框的文件入口能力不同，不将某入口支持格式外推到所有编辑入口。

## 后续人工标注协议

提供 `image-pair-evaluation/1` JSON：图片仅含匿名 ID、相对本地路径、SHA-256 和经采集记录确认的模态；每对提供 `duplicate: true/false/null`，定位另提供明确的 `positive` 及子图四角对应的原图归一化坐标。`null` 不进入混淆矩阵。

独立真实案例应先冻结抽样方案、图像与标签，至少由两名不参与算法调整的审阅者依据原始采集记录分别判断；分歧经复核，记录匿名审阅者、完成时间、依据、共识和疑难案例。审阅者在提交标签前不查看算法候选。保留同实验不同视野、不同通道、重复纹理、共享对照、覆盖标注及真实高位深案例，按模态分层，不因算法未命中而删除。用未参与调参的锁定集合运行同一离线评估器。

脚本要求 `studyType: independent_real_case_blind` 时显式提供 `annotationProtocol` 和盲测声明，但软件本身不能核验人工独立性。报告必须附标注流程及采样局限；当前没有这样的真实盲测结果。完整标注及图片保持本地，只在许可范围分享匿名统计。

## 性能优化和复核

旧 31.0649 s 数字保留在 [原验证记录](image-duplicate-validation.md)，属于 v1.4.4 合成图历史，不用来直接计算本轮加速比例。

本轮首先 profile 60 图：总计 25.766 s，其中 `knnMatch` 18.255 s、特征提取阶段 4.893 s；该诊断运行有采样/计时开销，不作为正式 P50/P95。由此只增加有界本地内存复用：描述子及几何候选/阴性 pair 结果缓存，写入满 5 分钟后不再复用，总预算约 24 MB，最多 4,096 条；不缓存图像载荷、文件路径、用户标签或报告。描述子最多占预算 3/4，比较结果预留 1/4，避免 60 图顺序重扫将全部 pair 记录挤出。

每次请求仍解码和核对源像素身份。不同源、ROI、分析大小或特征配置改变会使用不同 key；返回结果深拷贝，换 ID 或写复核备注不污染缓存。缓存是本机 worker 的进程内状态，不落盘、不跨进程或用户账户；TTL/LRU 在缓存读写时清理，闲置进程中的过期条目可能保留到下一次请求或进程退出。取消始终检查，不把部分结果作为完整报告返回。

正式同设备对照已完成：`scripts/benchmark_image_screening.py` 对 v1.4.19 和当前代码运行 5/20/60 图各 5 次。每次用新子进程；暖重复另在该子进程先完整预热一遍。记录见 [45 次原始计时、CPU、内存及取消结果](qa/round2/image-screening-performance.json)。测试期间未并行运行打包或全量绘图，仍有桌面系统正常调度波动，未使用干净虚拟机、限频 CPU 或低配置真机。

| 图片数 / 对数 | v1.4.19 P50 / P95（s） | 当前首次冷检查 P50 / P95（s） | 当前暖重复 P50 / P95（s） | 峰值工作集：基线 / 冷 / 暖（MiB） |
| --- | --- | --- | --- | --- |
| 5 / 10 | 0.815 / 0.876 | 0.767 / 0.915 | 0.216 / 0.278 | 106.2 / 108.5 / 108.3 |
| 20 / 190 | 4.686 / 6.848 | 5.304 / 6.323 | 0.920 / 1.080 | 156.6 / 166.8 / 165.6 |
| 60 / 1,770 | 32.853 / 35.553 | 32.078 / 33.978 | 8.062 / 8.538 | 283.7 / 301.1 / 305.4 |

60 图暖重复的 P50 较基线减少约 75%，平均 CPU 时间从 35.20 s 降至 9.96 s；它不是首次运行加速声明。20 图首次冷检查 P50 从 4.686 s 增至 5.304 s，缓存写入和正常调度有开销；不隐去这一结果。60 图首次 P50 的约 2% 差异不作为显著提升。所有 60 图运行都比较完整 1,770 对、报告 0 对匹配；这是速度用合成输入，不能建立特异度。

本次在进入 pair 阶段后另线程延迟 10 ms 请求取消，基线/当前冷/当前暖的停止延迟分别 0.115/3.050/0.160 ms；均抛出取消状态，没有返回部分完成报告。取消检查发生在有界原生调用之间，上述数值不是任意尺寸输入的最坏保证；从开始检查到可比较 pair 阶段约 7 s，准备阶段也保留取消检查点。

P95 是 5 个观测值的线性插值，不是生产尾延迟保证。CPU 记录采用进程 CPU 秒/墙钟时间，100% 代表一个逻辑核心，不能读成全机 CPU 占用。内存由 Windows `GetProcessMemoryInfo` 测得，包含原生 OpenCV/NumPy；暖样本的生命周期峰值包括预热，不能与仅测量阶段增量混淆。实际画布操作的交互验收由浏览器/安装版流程另行记录。

```powershell
.venv/Scripts/python.exe -X utf8 scripts/benchmark_image_screening.py `
  --baseline v1.4.19 --repetitions 5 --counts 5 20 60 `
  --out .cache/round2-validation/benchmark-final
```
